## Следующие частые commit/push

Один издатель для репозитория. Все следующие изменения публикуются небольшими коммитами непосредственно в `main`, без новых рабочих веток и PR. После каждого законченного инженерного участка сохранять WIP-коммит, не дожидаясь производственной готовности. Старые ветки и PR не удалять и не менять без отдельного поручения.

1. Согласовать с автором стабильный комплект. Получить схему, PCB, проект и используемые локальные библиотеки вместе; сравнить SHA-256 источника до/после чтения и копии. При изменении источника повторить снимок, не смешивать разные состояния. Временные файлы, локальные настройки, резервные копии и сторонние PDF не добавлять.
2. В чистом клоне проверить `git status --short --branch`, `git remote -v`, ветки/PR и права. Выполнить `git fetch origin`, `git switch main` и `git pull --ff-only origin main`. При расхождении историй разобрать точные коммиты и конфликты до записи; не угадывать инженерное решение. Force-push, перезапись чужой работы и изменение защиты веток запрещены.
3. Менять только согласованные пути аппаратной части/документов. Проверить приватные адреса, идентификаторы и служебные пути в публичных копиях, не меняя оригиналы. Обновить суммы и честный статус проверок; результаты ERC/DRC могут быть незавершёнными, но не выдуманными.
4. Добавить только явные пути через `git add <paths>`, просмотреть `git diff --cached --stat` и `git diff --cached`, выполнить `git -c core.whitespace=cr-at-eol diff --cached --check`, затем `git commit -m "hardware: WIP <конкретный участок>"`. Не использовать слепой `git add .` и не смешивать изменения прошивки/чужие коммиты.
5. Снова `git fetch origin`, проверить `git merge-base --is-ancestor origin/main HEAD` и выполнить обычный `git push origin HEAD:refs/heads/main`. Если удалённый main продвинулся, сначала безопасно включить его изменения и повторить проверки; при отклонённом push не применять force. Не оставлять контрольную точку только локально.
6. Прочитать `refs/heads/main` через `git ls-remote origin`, полное дерево через GitHub API и содержимое всех изменённых файлов по точному SHA. Сверить с локальными blob SHA и SHA-256. Передать https://github.com/krolbot/sirokko-26201-controller/tree/main, полный SHA, фактические проверки и оставшиеся ограничения. Для firmware брать только законченный переданный комплект отдельным коммитом main; старый аппаратный архив из него не восстанавливать.

Разовое объединение существующих веток в main выполняется обычными Git merge с сохранением истории и проверкой каждого исходного head через `git merge-base --is-ancestor`. Это не разрешение на force-push или удаление веток. Демоны, таймеры и автоматические фоновые резервные копии здесь не создаются. Публикация в main не означает производственный выпуск или допуск к эксплуатации.
