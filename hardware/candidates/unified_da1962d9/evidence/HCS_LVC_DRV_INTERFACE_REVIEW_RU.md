## 1. Фактические узлы

- `/SAFETY_OK`: U6.12 (SN74HCS11D), U6.4, U12.3, U11.11, J1.12, J25.6, R12.1, R88.1. R12 = 10 кОм ±1%, R88 = 4,7 кОм ±5%; оба вторыми выводами на GND.
- `/CLEAR_OK_BASE`: U3.10 (SN74HCS14D) → U14.6. Других DC-нагрузок в netlist нет.
- `/RELAY_DRIVER_OK`: U11.16 nFAULT → U14.3; R89 = 10 кОм ±1% на +3V3.
- `/CLEAR_OK`: U14.4 → U2.1 (асинхронный CLR latch), U6.2.
- U4 — SN74HCS30D. Его входы: PG_OK, WD_OK, STOP_OK, THERMAL_OK, ARM_READY, NOT_SW_TRIP; U4.11/U4.12 привязаны к +3V3.
- PG_OK формирует U7 TPS3839G33DBZR. U7.3 подключён к +3V3, U7.1 — GND, U7.2 — PG_OK. Это контроль +3V3, а не независимый контроль VM/P24.
- Сеть `PGOOD_5V` преобразователя существует отдельно; она не входит в эти входы U4.

## 2. Положительный ограниченный результат: CLEAR_OK_BASE

Для точного VCC = 3,0 В:
- HCS14 при нагрузке не более 20 мкА даёт VOH ≥ VCC−0,1 = 2,9 В и VOL ≤ 0,1 В.
- Единственный приёмник U14.6 — LVC1G97. Паспортный предел II = ±5 мкА при указанных TI условиях VI = 5,5 В или GND, VCC = 0…5,5 В.
- В таблице LVC для VCC = 3,0 В и −40…+125°C: VT+max = 1,87 В, VT−min = 0,84 В.
- Статические разности: HIGH 2,9−1,87 = 1,03 В; LOW 0,84−0,1 = 0,74 В.

Это положительная проверка нагрузочного бюджета/уровней в указанной расчётной точке с применением паспортного предела входного тока как инженерного бюджета. Она **не закрывает** весь диапазон VCC 3,0…3,6 В, фронты, power sequencing и задержки. Пороговую строку 3,0 В нельзя незаметно объявить гарантией для 3,3/3,6 В; II также имеет явно указанные паспортные условия.

## 3. SAFETY_OK нельзя принять по строке HCS «20 мкА»

Даже без тока входа DRV и других приёмников только два резистора дают:

```
I_PD(3,3 В, номиналы) = 3,3/10000 + 3,3/4700 = 1,032128 мА
I_PD,min(2,0 В) = 2,0/(10000×1,01) + 2,0/(4700×1,05)
                 = 0,603288 мА
0,603288 мА / 20 мкА = 30,1644
```

Второй расчёт использует максимальные сопротивления и минимальный требуемый HIGH для DRV (VIHmin = 2,0 В), а не предположение, что выход уже даёт полные 3,3 В. Ток через резисторы не может быть исключён из нагрузки источника.

В HCS11 loaded VOH при миллиамперной нагрузке указан для VCC = 4,5/6 В; перенос этих строк на питание 3,3 В не принят. Это **пробел документального подтверждения**, а не доказательство физической неработоспособности HCS11.

Уточнение по DRV: IIH = 100 мкА находится в столбце **MAX**, не TYP, но при VIN = 3,3 В и общем условии таблицы TA = 25°C. Предел не переносится автоматически на горячий режим и произвольное входное напряжение. Нельзя дополнительно прибавлять ток через типовой внутренний RPD = 100 кОм к IIH как независимую нагрузку: IIH уже характеризует вход.

## 4. nFAULT: статический предварительный расчёт, не full-range PASS

Для R89 ±1% верхняя оценка тока pull-up при VCC = 3,6 В:
`I <= 3,6/(10000×0,99) = 0,363636 мА` (до учёта входных утечек).

DRV задаёт VOLmax = 0,5 В при IO = 5 мА и IOHmax = 1 мкА при VO = 3,3 В; общее условие — TA = 25°C. Для LVC при точном VCC = 3,0 В низкий запас составляет 0,84−0,5 = 0,34 В. Условный HIGH-screen при бюджете утечки (1+5) мкА даёт `3,0−10100×6 мкА = 2,9394 В`; разность до VT+max = 1,0694 В.

Смешение разных паспортных точек в этом HIGH-screen явно условное. Это не гарантированная оценка на всём диапазоне питания/температур, не проверка nFAULT при VM = 0 и не доказательство времени захвата короткого fault-pulse.

## 5. Выявлен незакрытый сценарий восстановления 24 В

TI прямо пишет про nFAULT LOW при OCP/TSD. Для UVLO §7.3.2.3 гарантирует выключение схемы/выходов и автоматическое восстановление при возврате VM, **но не гарантирует nFAULT LOW**. Следовательно, нельзя подменять nFAULT отдельным сигналом «силовое питание исправно».

Рассмотрен случай, когда +3V3 удерживается (например, питание DevKit от USB или накопленная энергия), watchdog продолжает обслуживаться, а VM падает и возвращается. PG_OK от U7 в таком случае может оставаться HIGH: он контролирует +3V3. Выбран допустимый не исключённый даташитом угол: nFAULT не утягивает линию вниз при UVLO, R89 держит RELAY_DRIVER_OK = HIGH. Это не заявление об измеренном поведении DRV.

Идеальная логическая модель предназначенной схемы:

```
CLEAR_OK = CLEAR_OK_BASE AND RELAY_DRIVER_OK
SAFETY_OK = ALLOW_LATCH AND CLEAR_OK
GLOW_ENABLE_HW = GLOW_CMD AND SAFETY_OK
FUEL_CMD = FUEL_PERMIT AND SAFETY_OK
коэффициент включения каждой катушки = VM_VALID AND соответствующая команда
```

64 комбинации проверены вычислительным инструментом: при SAFETY_OK = 0 или VM_VALID = 0 все три катушки в модели выключены. Однако последовательность при удерживаемых командах и первоначальном ALLOW_LATCH = 1 даёт:

- VM есть, nFAULT HIGH → катушки включены;
- VM нет, nFAULT остаётся Hi-Z/HIGH → катушки выключены, но CLEAR_OK и ALLOW_LATCH не сбрасываются;
- VM вернулось → повторное включение без нового ручного разрешения **не исключено этой моделью**.

Положительный контроль: если реальный fault LOW достиг CLR и сбросил ALLOW_LATCH, последующий HIGH fault/возврат VM не включают катушки до нового разрешения.

### Требование к завершению входного блока

Проверить и обеспечить аппаратное снятие запомненного разрешения при квалифицируемой потере силового питания даже при сохранённых +3V3, USB и heartbeat. Возврат питания сам по себе не должен повторно разрешать топливо/свечу. Порог, длительность обнаружения и фильтр задаются отдельно по выбранной входной цепи и нагрузкам, а не назначаются произвольно этим логическим тестом.

Сначала проверить, можно ли надёжно использовать существующие power-good/силовые цепи, включая гарантированное состояние при VIN/VM = 0 и USB-backfeed. Наличие PGOOD_5V само по себе недостаточно. При необходимости добавить минимальный монитор силового питания; для входа в общую цепь предусмотрены свободные входы U4.11/U4.12, но их нельзя подключать слепо без electrical/timing qualification. FUEL_CMD и EXT_SAFETY_ENABLE не объединять. Архитектуру/медь по этому исследованию автоматически не менять.
