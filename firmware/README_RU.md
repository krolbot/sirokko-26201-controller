# Прошивка Sirokko 262.01

Последний опубликованный предварительный выпуск — **1.0.0-dev3** ([архив](https://github.com/krolbot/sirokko-26201-controller/releases/tag/v1.0.0-dev3)). В `main` подготовлена, но пока не выпущена крупная WIP-замена конфигурации процесса на типизированную модель ввода в эксплуатацию; локальное дерево ещё проходит полный цикл проверки и не должно считаться новым бинарным выпуском. Текущая программная приёмка и ограничения — [`docs/COMMISSIONING_MIGRATION_RU.md`](docs/COMMISSIONING_MIGRATION_RU.md). Исходные требования — [`../docs/FIRMWARE_IMPLEMENTATION_RU.md`](../docs/FIRMWARE_IMPLEMENTATION_RU.md).

## Реализовано

- Автоматическая температурная калибровка: один запуск, опора, ограниченные ступени, возвраты и повторы; без подтверждения каждой ступени. При отказе — прекращение подачи топлива и охлаждение. Новый диапазон применяется только после охлаждения и подтверждённой записи NVS.
- Температурный PI и ручной режим с ограничителем изменения команды. Достижение комнатной уставки не гасит отопитель; при недостаточно низкой минимальной мощности отображается предупреждение.
- Местные TFT ST7789, EC11 и короткая кнопка KEY0; меню, диагностика и журнал событий.
- Единственный таймер отключения, общий для TFT и веба. Публичный отложенный пуск исключён. Активные сроки и состояние RUN не восстанавливаются после сброса.
- Автономный русский веб-интерфейс через Wi-Fi AP, авторизация, одноразовые разрешения и привязка команды ко всему содержимому запроса.
- OTA только подписанным `.sota`, в неактивный раздел; проверка изображения, подписи, размера, целевого проекта и ESP32-S3. Подтверждение нового приложения и rollback предусмотрены в runtime.

## Целевая конфигурация

- YD-ESP32-S3 N16R8 V1.4; ESP-IDF **5.2.3**, target `esp32s3`.
- Flash 16 МБ, Octal PSRAM 80 МГц, CPU 240 МГц.
- HC-160A S2: только провод большой скорости; PWM 15 кГц, 12 бит, код не выше 4014.
- `GLOW_CMD`, `FUEL_CMD`, `FAN_REQUEST`, `SPEED_CMD` и остальные интерфейсы — `main/board.hpp`. PCB и аппаратная распиновка не менялись.
- TFT и EC11 — [`../docs/TFT24_INTERFACE_RU.md`](../docs/TFT24_INTERFACE_RU.md). Размер, поворот, сдвиги и инверсия TFT доступны в `idf.py menuconfig` → Sirokko local panel. Принятый экран — горизонтальный logical 320×240, native 240×320 с поворотом 90°; конкретное покупное исполнение ещё не измерено.
- KEY0: модуль12 → J32.12 → J3.8/GPIO40, active LOW, debounce 30 мс, опрос 10 мс. Долгое удержание не требуется. Удерживаемая при включении кнопка должна быть отпущена. Во время калибровки короткое нажатие фиксирует отрицательный операторский сигнал и STOP; отсутствие нажатия ничего не доказывает.

## Работа с таймером

Длительность: 0 — выключен, либо 1…10080 минут с шагом 1 минута. Один пункт «Таймер» в IDLE задаёт интервал до отключения после **следующего ручного** запуска; отсчёт начинается с принятия START, включая подготовку/розжиг. Изменение этой настройки не перезапускает уже идущий таймер.

«Выключить через» во время работы задаёт новый срок от текущего момента; 0 отменяет его. При достижении прежнего срока одновременно поступившая отмена/продление уже не спасает текущий запуск: выполняется STOP и охлаждение. Аварии и местная кнопка имеют приоритет.

## Точка доступа и OTA

При первом запуске создаётся случайный пароль AP и сохраняется в NVS. Пароль показывается **только на местной TFT-панели в меню Wi-Fi**, не в USB-логе, репозитории или диагностическом JSON. SSID: `Sirokko-XXXXXX`; адрес после подключения — `http://192.168.4.1`.

Сетевой код не пишет силовые GPIO. Цикл управления — отдельная задача с периодом 20 мс; запись настроек — отдельная задача и только при отключённых топливе/свече. HTTP имеет общий срок чтения 3 с, OTA — 120 с. На ошибке/обрыве OTA не выбирает новый загрузочный раздел. Сеанс браузера действует 15 минут. JSON с нулевым байтом отклоняется целиком. Финальная OTA-активация выполняется владельцем автомата через атомарное соревнование отмены и принятия записи; после принятия нельзя обещать отмену уже начатого выбора загрузочного раздела. Доступ через обычную команду OTA закрыт: нужен проверенный загрузочный пакет. В браузер встроен SHA-256 fallback для обычного HTTP AP.

Формат пакета, протокол и проверки — [`docs/WEB_OTA_IMPLEMENTATION_RU.md`](docs/WEB_OTA_IMPLEMENTATION_RU.md). Для выпуска подписанного файла:

```sh
python3 firmware/tools/sign_ota.py --input firmware/build/sirokko_26201_controller.bin --output sirokko-1.0.0-dev3.sota
```

Закрытый ключ хранится вне репозитория; собственный защищённый путь можно задать через `SIROKKO_OTA_SIGNING_KEY`. В образ встраивается только открытый ключ. Синтетические тесты создают собственный временный ключ, не используют ключ поставки.

## Сборка и программная проверка

Из корня репозитория (нужны Python 3, g++, Node.js, OpenSSL и заголовки libcrypto):

```sh
python3 firmware/tests/run_host_tests.py
```

Общий запуск компилирует 15 наборов ядра/панели/датчиков/runtime/OTA activation, полный набор web/OTA и клиентские JS-тесты. `--sanitize` повторяет C++ проверки с ASan/UBSan. Автономный веб, встраивание и Chromium/WebKit — [`web_ui/README_RU.md`](web_ui/README_RU.md). Сценарии используют явно синтетические данные, а production HTTP-handlers проверяются с тестовым транспортом — это не настоящий ESP32/AP.

В окружении ESP-IDF 5.2.3 из `firmware/`:

```sh
idf.py set-target esp32s3
idf.py build
```

Проверенный контейнер: `espressif/idf@sha256:9cd723f013e1a8b22aeed61c02e3248bb11e8f2e2ae333cee08a18b9e36c1380`.

Состав начальной прошивки из одной сборки определяется `build/flasher_args.json`:

- `0x0 bootloader/bootloader.bin`;
- `0x8000 partition_table/partition-table.bin`;
- `0x10000 ota_data_initial.bin`;
- `0x20000 sirokko_26201_controller.bin`.

Не смешивать файлы разных сборок. Успех локальной сборки не означает публикацию или успешный GitHub CI. Поставка должна содержать точный снимок исходников и контрольные суммы; для незафиксированного Git-дерева нельзя выдавать HEAD за ревизию изменённых файлов.

Исторические приёмки выпущенных версий: [`docs/ACCEPTANCE_DEV3_RU.md`](docs/ACCEPTANCE_DEV3_RU.md) и [`docs/ACCEPTANCE_RU.md`](docs/ACCEPTANCE_RU.md). Они не подтверждают незавершённую WIP-замену.

## Физически неизвестные параметры

В WIP-контракте `SafetyEnvelope` содержит исходные ограничения конкретной аппаратной сборки, а `LearnedOperatingModel` — измеренный автоматической калибровкой рабочий диапазон и его происхождение. При отсутствующей или неверной исходной записи контроллер остаётся в безопасном запрете подачи топлива; значения из тестовых данных не используются. Ручная коррекция может только сузить уже полученную модель и требует совпадающей ревизии. Ни ввод ограничений, ни численно допустимая модель сами по себе не доказывают физическую квалификацию горения.

Две K-термопары измеряют выход выхлопа и горячий воздух. Падение температуры после снижения команды не равно погасанию; ровная температура может быть остаточным теплом; более горячий воздух при меньшем расходе не обязательно означает большую тепловую мощность. Калибровка отбраковывает несогласованные данные, но не измеряет CO/O₂, дымность, RPM, ток или расход.

Для текущего локального дерева повторно прошли 15 host-наборов ядра/панели/runtime плюс web/OTA, те же проверки с ASan/UBSan, 22 клиентских теста, production-сборка веб-интерфейса и сверка встроенной страницы. Сценарии NVS используют модельный backend; они не заменяют реальные ESP32 flash brownout-тесты. Полная браузерная проверка и интегрированная сборка ESP-IDF для этого точного незакоммиченного дерева ещё требуют подтверждения. Физические GPIO, питание, NVS при пропадании питания, OTA-перезагрузка/rollback и горение не проверены.
