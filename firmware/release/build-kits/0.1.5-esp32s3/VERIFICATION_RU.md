# Sirokko 262.01: проверка моторного выхода 0.1.5-DRAFT

Статус: DRAFT / BENCH ONLY. Это программная доработка и проверяемая сборка, не квалификация LTC7001/IRFB4110, не испытание платы и не разрешение топлива, накала или горения.

## Исправленная причина

Прежнее преобразование `1000*1023/1000` давало 1023 тика на период из 1024: расчётные 99.90234375%, не постоянный HIGH. Расчётный LOW-интервал при 20 кГц — 48.828125 нс. Это модель, а не осциллограмма. В новой версии 1000 вообще не преобразуется в duty: применяется штатный `ledc_stop(LEDC_LOW_SPEED_MODE, LEDC_CHANNEL_0, 1)`. Для 0 используется такой же stop с idle 0. Повторная команда DC не запускает PWM.

Для `1..800` новые ticks сначала записываются `ledc_set_duty`, затем `ledc_update_duty` вновь разрешает сигнал. Фактическое программное квантование — `round(permille*1024/1000)` тиков на 1024: запрос 1 даёт 1 тик, 800 — 819 тиков, то есть 799.8046875‰. Это не измеренная электрическая скважность и не точное равенство введённой величине. 1000 означает именно постоянный уровень. Значения 801..999 отвергаются, а не заменяются на 800.

Частота ограничена сверху 20 кГц. Для фиксированных APB 80 МГц и 10 бит SDK использует 18-битный делитель с 8 дробными битами: при 76 Гц получается 263158, выше максимума 262143; при 77 Гц — 259740, при 20 кГц — 1000. Поэтому допустимый ввод — 77..20000 Гц. Кроме программного расчёта проверяются возвраты `ledc_timer_config`, `ledc_channel_config`, `ledc_set_duty`, `ledc_update_duty`, `ledc_stop` и фактический результат `ledc_get_freq`.

## Согласованный путь управления

- CLI проверяет те же границы, что `validate_config`; токен не обходит валидатор, прямой accepted-запрос записи в NVS также проверяется.
- Старый schema-2 blob с корректным digest, но недопустимыми числами сохраняет числа без подрезания, теряет приёмку в памяти, сообщает `CONFIG_PWM` и не разрешает START. Schema 1 не мигрируется.
- Изменение/приёмка/отзыв профиля разрешены только с выключенными мотором, топливом, permit и накалом. Проверка и проход автомата/вывода сериализованы одним mutex. Любая разрешённая попытка изменения запрещает START до reboot; CLI никогда не перенастраивает живой адаптер.
- Ошибка выходного API защёлкивает адаптер в отказе до reboot. Все независимые отключения пробуются без короткого замыкания цепочки: FUEL/FUEL_PERMIT/GLOW/ARM/heartbeat/FAN OFF, SW_TRIP ON, LEDC stop LOW и отдельное отсоединение GPIO17 от LEDC с GPIO LOW. Следующие проходы повторяют отключение, старый HIGH/PWM не воспроизводится. Первичная ошибка и совокупный результат отключения журналируются один раз, без затопления журнала.
- `status`: requested_speed — запрос автомата; applied_speed — последняя успешная программная команда (0 при отказе); output_ok — здоровье адаптера. Никакое из этих полей не является электрической обратной связью.
- При обычном STOP/перегреве сначала снимается топливо, затем сохраняется максимальная постпродувка 1000 как постоянный HIGH. GPIO17 становится LOW по фактической команде 0. Только отдельный отказ выходной подсистемы требует немедленного отключения мотора. Автопуск, двухскоростной профиль и автономный heartbeat не добавлены.

## Что выполнено на компьютере

Свежий исходный main содержал 40 тестов, а не 39 из старого описания. Сохранены все 40; добавлены 10 групп. `logs/host-tests.log` содержит RESULT 50/50 passed. Компилируются настоящие `output_driver.cpp` и `commissioning.cpp`, подменены только API IDF/GPIO/LEDC/NVS.

Покрыты частоты 0/1/76/77/20000/20001/78125; duty 0/1/800/801/999/1000/1001; OFF→PWM→DC→PWM→OFF и повтор DC; ошибки timer/channel/get_freq/stop/set_duty/update_duty/GPIO; повторные отказы и постоянный отказ stop LOW при источнике DC; реальные старые NVS blobs с корректным digest и неверными границами; CLI integer overflow/token/прямая accepted-запись; FAULT_OUTPUT из RUN_LOW/RUN_HIGH; CONFIG edit inhibit; recovery 1000 и сохранение максимальных этапов/тепловой постпродувки. Полный старый набор проверяет STOP, ручные RESET/START после возврата питания, датчики, экран и watchdog.

Тесты вызовов подтверждают логику адаптера; они не исполняют регистры ESP32 и не являются RTOS-тестом гонок. Сериализация CLI проверена по коду; её время вместе с NVS/TFT и физическим STOP нужно измерить на плате. Результаты чистой целевой сборки и разбора образов находятся в отдельных исходных журналах комплекта.

## Первичные источники ESP-IDF 5.5.2 / именно ESP32-S3

- Документация LEDC: https://docs.espressif.com/projects/esp-idf/en/v5.5.2/esp32s3/api-reference/peripherals/ledc.html
- Реализация `ledc_stop`, `ledc_update_duty`, `ledc_calculate_divisor`: https://github.com/espressif/esp-idf/blob/v5.5.2/components/esp_driver_ledc/src/ledc.c
- ESP32-S3 HAL: https://github.com/espressif/esp-idf/blob/v5.5.2/components/hal/esp32s3/include/hal/ledc_ll.h

`ledc_stop` задаёт idle, отключает signal output и duty start, затем обновляет low-speed channel. `ledc_update_duty` вновь разрешает signal output/duty start с новым duty. Это не предположение по ESP32 classic и не обход официального API. Аппаратное ограничение взято из инженерного `motor_gate_supply_qualification.md`, раздел ограничения прошивки (LTC7001 + IRFB4110 candidate).

## Обязательный стенд — не выполнен

Без топлива/накала осциллографом проверить:

1. Реальные frequency/duty для 1..800, в том числе 1 и 800, на выбранных частотах до 20 кГц.
2. При 1000 — отсутствие повторяющихся LOW-провалов; повтор DC и оба перехода PWM↔DC; отсутствие старого duty после возобновления PWM.
3. LOW при действительной команде 0; OFF→PWM→DC→PWM→OFF.
4. Отказ адаптера из PWM и DC: топливо/permit/накал сняты, SW_TRIP активен, GPIO17 LOW, в том числе при отказе LEDC stop. Аппаратно отказавшие MCU/GPIO программой не гарантируются — аппаратные подтяжки/watchdog/защёлка/независимый выбег обязательны.
5. Штатные STOP/перегрев: снятие топлива раньше постпродувки, сохранение 1000 до её окончания и последующий LOW; никаких новых автоматических розжигов.
6. Физический RESET, новые фронты START, реальные интервалы heartbeat и длительность прохода с TFT/NVS/CLI. Сборка этого не доказывает.

Hardware, Murata-снимок, старые комплекты и соседние сервисы не изменяются этой доработкой. Возможности зависимой задачи t_041c7f7b в неё не включены.
