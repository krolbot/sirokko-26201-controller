# TFT SPI: исправление 0.1.7-DRAFT и границы проверки

Статус: программная конфигурация исправлена; электрическая/аппаратная квалификация НЕ выполнена. Плата не подключалась, топлива/силовых нагрузок/огневых опытов не было.

## Основание

[ST7789V v1.3, 2014/03](https://www.newhavendisplay.com/appnotes/datasheets/LCDs/ST7789V.pdf), §7.4.3/Table6 (p44), four-line SPI: минимальный write cycle 66ns, CS setup/hold 15ns, CS-high 40ns, D/C и DATA setup/hold 10ns, rise/fall не более 15ns, Ta −30…70°C, VDDI 1.65…3.3V. Это краткие атрибутированные параметры; документ с маркировкой Sitronix Confidential полностью не копируется.

Ранее выбранные 20MHz означали 50ns — меньше 66ns. Успешная компиляция и host-тесты не делали такой режим допустимым для модуля. Комплект 0.1.6-DRAFT отозван как итоговый; его исторические файлы не изменены (см. `release/NOT_FOR_USE_0.1.6_RU.md`).

## Единый production-путь

- `board.hpp`: TFT 10MHz, mode0, CS47/DC48; `cs_ena_pretrans=1`, `cs_ena_posttrans=1` — номинально 100ns до/после SPI, вместо неявных значений SDK. GPIO и аппаратная конструкция не менялись.
- `display_geometry.hpp`: единственные размеры UI — 240×320, 20 строк/полосу, 16 полос/кадр. Renderer, адаптер, host-тесты и изображения используют этот заголовок. Две физические полосы сохраняют прежний логический блок из двух строк текста; 40 строк не являются DMA-буфером.
- Буфер: 240×20×2 = 9600 bytes. Провод одной полосы: 9600×8/10MHz = 7.68ms; 40 строк при новой частоте заняли бы 15.36ms и поэтому отвергнуты. Полный кадр: 122.88ms только пикселей, без команд/планировщика. Пределы компилируются как static assertions.
- `LocalDisplay`: один DMA-буфер, очередь глубины 1, не перезаписывает буфер до callback; один снимок `UiFrame` на все 16 полос. Уже существующий timeout 50ms сохранён: wire-бюджет одной полосы не увеличен. Тайм-аут проверяется при следующем проходе UI, это не обещание абсолютной задержки на плате.
- MAX31856 остаются mode1/5MHz, CS9/CS10; общие только MOSI11/SCK12 SPI2. Отдельного драйвера/шины/второго автомата не добавлено. Control task не ожидает TFT; свежесть датчиков и неисправность UI продолжает проверять основной автомат. Тайминги горения не менялись.

## Что проверено в ESP-IDF 5.5.2

Официальные исходники:

- [`esp_lcd_io_spi.h`](https://github.com/espressif/esp-idf/blob/v5.5.2/components/esp_lcd/include/esp_lcd_io_spi.h): CS pre/post задаются в SPI bit cycles.
- [`esp_lcd_panel_io_spi.c`](https://github.com/espressif/esp-idf/blob/v5.5.2/components/esp_lcd/spi/esp_lcd_panel_io_spi.c): поля передаются в `spi_device_interface_config_t`, устройство half-duplex, D/C задаёт pre-transfer callback; command/param транзакции используют SPI_TRANS_CS_KEEP_ACTIVE для связанной передачи, завершение данных освобождает CS.
- [`spi_master.c`](https://github.com/espressif/esp-idf/blob/v5.5.2/components/esp_driver_spi/src/gpspi/spi_master.c), строки 548–555: значения идут в HAL `cs_setup`/`cs_hold`; строки 833–838: pre_cb вызывается ДО `spi_hal_user_start`. Поэтому D/C выставляется до начала CS/clock, а явный CS setup даёт номинальный запас. Это анализ software-пути, не осциллограмма.

Пара pre/post сама по себе НЕ доказывает CS-high≥40ns между транзакциями, D/C/data hold на выводах, Tr/Tf≤15ns, отсутствие помех и времён переключения SPI mode. В `esp_lcd_panel_io_spi_config_t` нет отдельного параметра CS-high; ложный физический допуск по этим полям не выдаётся.

## Повторные программные проверки

Полный suite: 97/97 C++ (50 baseline, 11 feature, 11 runtime, 4 display/SPI-model, 4 UI, 17 network) + 4/4 Python. `display_tests.cpp` компилирует настоящий `local_display.cpp` и настоящее ядро: проверяет переданную SDK конфигурацию, все 16 полос, целостность кадра, охранные слова вокруг буфера, неизменность активного DMA, stalled/error путь и топливный OFF без отмены продувки.

10-секундная модель serial-bus: пиксели/11 bytes команд/условный запас 10us сериализованы; запросы обоих MAX приходят ВО ВРЕМЯ TFT DMA, а не только в свободную щель. 501 проход control, 250 спадов heartbeat, максимальный период спадов 40ms; максимальное ожидание MAX 7625us, 3001 абстрактная транзакция, пересечения CS-владения отвергаются. STOP приводит к OFF топливо/накал и сохраняет запрос продувки. Подменённые SDK/RTOS/датчики не измеряют реальный IRQ/планировщик/MAX conversion/freshness/CS waveform; нельзя выдавать эти числа за стендовую осциллографию. Существующая аппаратная watchdog-защита не заменена моделью.

12 PNG 240×320 + contact sheet получены из фактических production render-буферов с новой геометрией. Визуально проверены все 12: вторые строки/кириллица/версия 0.1.7-DRAFT/цвета сохранены, пропавших/дублированных 20-строчных полос не видно. Это симуляция, не фото TFT.

Точная target-сборка и соответствие source commit — в manifest/журнале нового `release/build-kits/0.1.7-esp32s3/`; результат 0.1.6 НЕ подменяет её.

## Обязательный следующий физический стенд, только без топлива

На выводах реального модуля измерить: 10MHz и write cycle≥66ns; CS setup/hold≥15ns, high≥40ns; D/C/DATA setup/hold≥10ns, rise/fall≤15ns; отсутствие одновременных CS9/10/47; MAX mode1/5MHz и TFT mode0/10MHz. Проверить supply/уровни/проводку, холодный старт/цвета/всю кириллицу, возраст реальных температур и задержки STOP/heartbeat при непрерывном TFT, обрыве/зависании SPI и ошибках NVS/сети. До этого нельзя заявлять электрическую пригодность модуля, аппаратную работоспособность или допуск горелки.
