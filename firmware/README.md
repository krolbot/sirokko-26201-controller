# Разработка и сборка прошивки

Для записи готовой прошивки и первоначальной настройки используйте [руководство пользователя](../docs/user-guide.md#первоначальная-настройка).

## Инструменты

- ESP-IDF **5.2.3**, настроенный для **ESP32-S3**;
- Node.js **26** с npm;
- Python 3 из окружения ESP-IDF.

Версии компонентов ESP-IDF и веб-зависимостей закреплены в `dependencies.lock` и `web_ui/package-lock.json`.

## Собрать

Откройте терминал с активным ESP-IDF. Все команды ниже запускаются **из корня репозитория**:

```sh
npm ci --prefix firmware/web_ui
npm run build --prefix firmware/web_ui
python3 firmware/tools/embed_web_ui.py
python3 firmware/tools/embed_web_ui.py --check
idf.py -C firmware set-target esp32s3
idf.py -C firmware build
```

Результат — `firmware/build/`. Для USB-записи своего образа на вынутый из основной платы DevKit:

```sh
idf.py -C firmware -p /dev/ttyACM0 flash monitor
```

Замените порт фактическим. GitHub Actions собирает ту же цель и сохраняет комплект с загрузчиком, таблицей разделов, образами и адресами записи.

## Где изменять

| Каталог / файл | Назначение |
|---|---|
| `components/control_core/` | Управление отопителем и регулирование |
| `main/board.hpp` | Аппаратные назначения |
| `main/app_main.cpp`, `main/sensors.cpp` | Работа ESP-IDF и датчиков |
| `main/panel*` | Экран и местное управление |
| `main/web*`, `web_ui/src/` | HTTP API и веб-интерфейс |
| `main/persistence.hpp`, `main/record_codec.hpp` | Хранение параметров |
| `partitions.csv`, `sdkconfig.defaults` | Разделы flash и конфигурация сборки |

Шрифты, иконки и встроенная веб-страница лежат в `main/*_data.inc`.

### Изменение веб-интерфейса

Правьте `web_ui/src/`, затем повторите сборку веб-страницы, `embed_web_ui.py` и сборку ESP-IDF. [Подробности веб-сборки](web_ui/README.md).

### Изменение шрифта и иконок

Генераторы находятся в `tools/`; нужны Pillow/FreeType и `rsvg-convert`. Для обычной сборки уже включённых данных эти инструменты не нужны. При изменении ресурсов запускайте генераторы из корня репозитория и проверяйте результат:

```sh
python3 firmware/tools/generate_panel_fonts.py
python3 firmware/tools/generate_panel_icons.py
```

Результат генерации зависит от версий Pillow и FreeType.

## Подпись OTA

Веб-обновление принимает `.sota`, подписанный RSA-3072. Открытый ключ доверия включён в `main/ota_public_key.pem`; закрытый ключ в проект не входит.

Из корня репозитория, после сборки:

```sh
python3 firmware/tools/sign_ota.py \
  --input firmware/build/sirokko_26201_controller.bin \
  --output /path/to/sirokko.sota \
  --key /protected/sirokko-ota-rsa3072.pem
```

Путь к закрытому ключу задаётся параметром `--key` или переменной `SIROKKO_OTA_SIGNING_KEY`. Файл ключа должен быть доступен только владельцу.

Для собственной системы обновлений нужен собственный ключ и соответствующий открытый ключ в прошивке. Сначала запишите такую прошивку через USB. Не публикуйте закрытый ключ вместе с исходниками или выпуском.

Первоначальные пределы задаются в **Настройки → Параметры отопителя**. [Руководство](../docs/user-guide.md#первоначальная-настройка); [подготовка заводской NVS](../docs/factory-envelope.md).

## Проверки

Нужны g++, OpenSSL development headers, Python 3 и Node.js. Из корня репозитория:

```sh
python3 firmware/tools/test_host.py
node --test firmware/web_ui/tests/*.test.mjs
```

Тесты управления, хранения, протокола, панели и OTA исполняются на компьютере с `-Os` и ASan/UBSan. Входы искусственные, COM-порт не используется. Подпись OTA проверяется временным RSA-3072 ключом.

Подключитесь к AP и откройте `http://192.168.26.1/`. DHCP выдаёт адрес 192.168.26.x без DNS. Неизвестные HTTP-маршруты возвращают 404, перенаправлений нет.

## Сборка и обработка отказов

Сборка использует `-Os`, сохраняет assertions, аппаратные watchdog и проверки переполнения стека FreeRTOS. Дополнительно включены `-fstack-protector-strong` и аппаратная контрольная точка на границе стека. Размеры стеков не уменьшены. Для существующего каталога сборки эти параметры нужно перенести в активный `sdkconfig`: defaults не заменяет выбранные ранее настройки. Основание: [настройки компилятора ESP-IDF](https://docs.espressif.com/projects/esp-idf/en/v5.2.3/esp32s3/api-reference/kconfig.html#config-compiler-optimization) и [контроль использования RAM](https://docs.espressif.com/projects/esp-idf/en/v5.2.3/esp32s3/api-guides/performance/ram-usage.html).

При отказе регистрации HTTP-маршрутов сервер останавливается и освобождает ресурсы. Отклонённые запросы с телом завершаются закрытием соединения: сервер не дочитывает потенциально неограниченный поток. Для принимаемых команд и OTA остаются ограничения размера и общего времени чтения. Обработчики следуют [контракту ESP-IDF HTTP Server](https://docs.espressif.com/projects/esp-idf/en/v5.2.3/esp32s3/api-reference/protocols/esp_http_server.html).

Ошибки выделения ресурсов управления и начальной установки выходов записываются в журнал. Если watchdog перестаёт принимать подтверждения от задачи управления, топливо и свеча выключаются, фиксируется ошибка управления. Переполнение очереди результата записи фиксирует отказ хранения вместо бессрочного ожидания. Эти меры и программные тесты не являются сертификацией по MISRA или IEC 61508; испытания с отопителем остаются отдельным этапом.

## Длинные HTTP-заголовки мобильных браузеров

`CONFIG_HTTPD_MAX_REQ_HDR_LEN=8192` задан в `sdkconfig.defaults`. Для существующей сборки обновите также активный `sdkconfig`: ESP-IDF не заменяет его значениями defaults. Проверка при компиляции не позволит собрать веб-сервер со старым лимитом 512 байт.

Основание: [настройка ESP-IDF 5.2.3](https://docs.espressif.com/projects/esp-idf/en/v5.2.3/esp32s3/api-reference/kconfig.html#config-httpd-max-req-hdr-len).

`tests/http_server_smoke.cpp` — интеграционная проверка на отдельном DevKit с питанием только от USB. Для тестовой сборки добавьте файл в SRCS, объявите `void http_server_smoke_start();` в глобальной области `app_main.cpp` и вызовите функцию после успешного запуска веб-сервера. Проверяются отсутствие DNS и перенаправлений системных HTTP-проб, заголовки 2–4 КБ, главная страница, состояние, история с полученным сеансом, неизвестный API, отказ 431 для запроса свыше 8 КБ, немедленное закрытие отклонённых загрузок и последующая доступность панели. Ожидается журнал `RESULT 19/19` с показателями внутренней памяти. В обычную прошивку тест не включён.

Буферы веба для JSON, Cookie и снимка истории размещены в PSRAM платы N16R8 через `EXT_RAM_BSS_ATTR`. Это освобождает внутреннюю память для стеков задач и DMA. Требуется `CONFIG_SPIRAM_ALLOW_BSS_SEG_EXTERNAL_MEMORY=y`, в том числе в активном `sdkconfig` существующей сборки. Само кольцо истории остаётся во внутренней RAM. При отказе запуска HTTP журнал содержит причину, свободную внутреннюю память и размер её наибольшего блока. [Размещение BSS в PSRAM](https://docs.espressif.com/projects/esp-idf/en/v5.2.3/esp32s3/api-guides/external-ram.html#allow-bss-segment-to-be-placed-in-external-memory).

## Готовность контроллера

Прошивка одна для ESP и собранного контроллера. USB не выбирает режим. При отсутствии проверенного профиля отопителя ядро находится в `UNCONFIGURED`: силовые выходы выключены, продувка и таймер не запускаются. Настройки, диагностика, Wi-Fi и обновление доступны через тот же интерфейс.

При подтверждённом завершении предыдущего цикла ядро начинает с `IDLE`, без продувки. Прерванный цикл или отсутствие достоверной записи у настроенного отопителя требуют восстановительной продувки. Если одновременно отсутствуют профиль и запись цикла, до настройки сохраняется чистая отметка: нагрев ещё не был разрешён. Пуск требует свежих показаний, успешного запуска драйверов местного управления и заполненного профиля. Отсутствие профиля не означает, что прошивка обнаружила отключённую плату: датчика подключения платы нет. Инициализация SPI-панели также не доказывает её физическое наличие.

После OTA образ подтверждается при исправном цикле управления, выходном драйвере, хранилище и веб-сервере; у настроенного отопителя дополнительно проверяется инициализация местного управления и датчиков. Проверки должны проходить непрерывно секунду в течение первых десяти секунд после запуска сервисов. При неуспехе образ не подтверждается, нагрев заблокирован.

Стек задачи запуска — `CONFIG_ESP_MAIN_TASK_STACK_SIZE=8192`. При обновлении существующего `sdkconfig` задайте это значение явно; проверка при компиляции не позволит оставить прежние 3584 байта. После инициализации журнал сообщает оставшийся запас стека.

## Владение состоянием

- `control_core`: переходы, ограничения, выходные команды; не обращается к FreeRTOS и GPIO.
- `app_main.cpp`: единственный владелец контроллера, очереди команд, NVS-транзакции и применение выходов.
- `network.cpp` / `network_config.hpp`: AP, пароль, адрес и запуск сетевых сервисов.
- `web.cpp`: HTTP, вход, команды и загрузка; `web_state.cpp`: представление состояния.
- `command_policy.hpp`: единая доступность действий для JSON `commands`, выдачи разрешений и приёма команд. Ядро повторно проверяет условия при исполнении; STOP обходит допуск обычных команд.
- `web_sessions.hpp`: восемь независимых браузерных сеансов, истекающих через 15 минут бездействия; активные не вытесняются. При заполнении возвращается `SESSIONS_FULL`.
- `CommandGate`: до 16 одноразовых разрешений на пять секунд. STOP аннулирует все. Изменение состояния делает предыдущие разрешения недействительными.

Настройки записываются в `settings_v3`. Старый формат не читается и не мигрируется: при первом запуске этой версии применяются начальные пользовательские настройки. Пароль Wi-Fi и профиль отопителя используют отдельные записи.

## Параметры

Настройки интерфейса (15–30 °C, шаг 1 °C; ручная команда с шагом 5%) и коэффициенты PI — политика текущей реализации, не паспортные характеристики отопителя. Ограничения собраны в `control.hpp`, коэффициенты — в `RegulatorConfig`. Параметры горения задаются отдельно в `SafetyEnvelope`; подтверждённые инструкцией начальные значения и ограничения перечислены в [таблице параметров](../docs/heater-sources.md).

Диапазон проверки термопары допускает отрицательные температуры: нижняя граница −200 °C соответствует типу K в [MAX31856, таблица 1](https://www.analog.com/media/en/technical-documentation/data-sheets/MAX31856.pdf). Это диапазон измерения, не рабочая температура отопителя. Верхнее программное ограничение 600 °C и заданные меньшие пределы перегрева сохранены.

Перед пуском в NVS сохраняется `cycle_v1 = 1`. Команда остаётся в очереди до подтверждения записи; ядро дополнительно проверяет `cycle_record_ready`. После завершения охлаждения, выключения выходов и обработки очереди сохраняется `cycle_v1 = 0`. Запись выполняет существующая задача хранения, без ожидания флеш-памяти в контуре управления.

Нулевая проверенная запись означает обычный запуск без продувки. Единица, отсутствие записи или повреждение означают восстановление с продувкой; нагрев и таймер автоматически не возобновляются. При первом обновлении старого настроенного устройства запись отсутствует: одна восстановительная продувка формирует исходную отметку завершения. Ошибка записи блокирует пуск. Одна лишь причина перезапуска ESP не используется: она не сообщает, работал ли отопитель перед отключением питания.

Документация NVS: https://docs.espressif.com/projects/esp-idf/en/v5.2.3/esp32s3/api-reference/storage/nvs_flash.html. Новая запись может не сохраниться при обрыве питания во время её записи, поэтому нагрев начинается только после подтверждения отметки, а отметка завершения записывается после охлаждения.

### Изменение исходных пределов

Команда `PROFILE` использует общую выдачу разрешения, привязку полного содержимого SHA-256, очередь управления и задачу хранения. Принимается полный `SafetyEnvelope` без пользовательского флага `provisioned`; времена, температурные соотношения, рабочий диапазон ШИМ проверяются перед выдачей разрешения и повторно при применении. Допуск — `UNCONFIGURED` или `IDLE`, без аварии, занятости хранилища и активных выходов.

Задача хранения сохраняет профиль в `envelope_v6` с контрольной суммой и проверкой чтением. Только после подтверждения владелец управления меняет профиль в RAM и увеличивает версию состояния. Сбой записи блокирует дальнейшие пуски. Прежний профиль с границей исследования не читается как рабочий диапазон; пользовательские настройки и Wi-Fi не меняются.

При первом запуске без профиля и без записи цикла сохраняется чистая отметка. Только после подтверждения её записи первоначальное заполнение оставляет `IDLE`. Настроенный отопитель без достоверной записи цикла и любой отопитель с отметкой прерванного цикла сохраняют требование продувки. Новая авария во время записи не снимается установкой профиля. Проверка в браузере ждёт новых сохранённых параметров, исправного хранилища, а не ответа `QUEUED`.

API состояния отдаёт `envelope.parameters`, ограничения валидатора в `envelope.limits` и `hardware.local_controls_initialized`. Последнее поле сообщает об инициализации драйверов, не о наличии экрана или кнопки на разъёме.

Местная панель и веб получают допуск пуска через общую `command_policy`. Нижний ручной уровень обе стороны вычисляют из профиля одинаково, с округлением вверх до шага 5%.
