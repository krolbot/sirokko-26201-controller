# Автономное ядро температурной калибровки

## Назначение и граница

`calibration.hpp` / `calibration.cpp` — allocation-free C++17-ядро конечного автомата. Оно не включает `control.hpp`, не управляет GPIO, топливом, свечой, продувкой, сохранением NVS или GUI.

Родительская safety FSM обязана:

1. выполнить обычный разрешённый запуск;
2. вызвать `Calibrator::start()` только после перехода в штатный `RUN` с включённой известной командой топлива и уже выключенной свечой;
3. применять `Snapshot::target_code` своим существующим ограничителем плавности;
4. на каждом цикле вернуть в `Observation::commanded_code` **фактически достигнутую** команду, а не желаемую;
5. при `stop_requested` выполнить штатный STOP: немедленно убрать топливо по собственной защите и сохранить требуемое охлаждение/продувку;
6. сохранить новый профиль только если после STOP/cooldown всё ещё есть `completed_pending_stop == true` и `result.profile.valid == true`.

Калибратор не делает auto-restart, не запрашивает увеличение команды для восстановления подозрительного горения и не меняет прежний профиль. На `FAILED`/`CANCELLED` результат не содержит профиля.

## Минимальный API

```cpp
#include "sirokko/calibration.hpp"

sirokko::calibration::Calibrator calibration;

// cfg вводится сервисом процесса; в модуле нет скрытого физического PWM-минимума.
if (!calibration.start(cfg, now_ms)) {
    // calibration.snapshot(now_ms).stop_requested == true для invalid Config.
}

sirokko::calibration::Observation observation{};
observation.now_ms = now_ms;
observation.exhaust = {exhaust_milli_c, exhaust_sample_ms, exhaust_status, exhaust_valid};
observation.hot_air = {air_milli_c, air_sample_ms, air_status, air_valid};
observation.commanded_code = actual_limited_code;
observation.run_active = parent_state_is_run;
observation.fuel_commanded = fuel_command_is_on;
observation.glow_commanded = glow_command_is_on;
observation.operator_negative = debounced_key0_short_press;
const auto state = calibration.tick(observation);

// Parent drives this target only through its own slew limiter.
const uint16_t requested_code = state.target_code;
if (state.stop_requested) {
    // parent STOP/fuel cutoff/cooldown FSM
}
if (state.completed_pending_stop && state.result.profile.valid) {
    // persist only after the parent completed stop/cooldown
}
```

`operator_negative` — одно уже подавленное короткое событие KEY0. Отсутствие события ничего не подтверждает. `status == 0` и `valid == true` обязательны для обоих температурных каналов.

## `Config`: что задаётся снаружи

Все поля намеренно обязательны; нулевые/противоречивые значения дают `INVALID_CONFIG` и STOP-сигнал. В частности задаются:

- закрытый исследовательский интервал `floor_code..ceiling_code`; оба кода ненулевые, а `ceiling_code` — фактически проверяемая опора и будущий `max_code`;
- `step_code`; интервал обязан содержать как минимум две нижние точки, чтобы одна из них осталась запасом;
- частота/зазоры/свежесть/скос времён двух датчиков;
- тайм-ауты получения достигнутой команды, опоры, точки и всего процесса;
- числа для статистики: верхние границы и нижние полы шума/дрейфа опоры, множители повторяемости и минимально различимый отклик;
- допустимые потолки реально наблюдаемого `slew_up/down` для родительского ограничителя.

Прототип исследования — три окна по 60 отсчётов при 1 с. В ядре жёстко три неперекрывающихся окна, но `samples_per_window` и `sample_period_ms` вводятся явно. Это не время, в течение которого можно ждать подозрительное горение. Тест использует укороченное `8 × 1 с` окно только для синтетического объекта.

`floor_code`, безопасные параметры пуска/перегрева и рабочие потолки скоростей должны прийти из отдельной конфигурации процесса/сервиса. Ядро не назначает реальный PWM-минимум и не интерпретирует тестовые числа как огневые пределы.

## Алгоритм

1. Запрашивает `ceiling_code` и ждёт, пока `Observation.commanded_code` реально его достигнет.
2. На неподвижной опоре набирает три окна. Для каждого канала считает наклон линейной регрессии, p90–p10 остатков и разброс средних окон.
3. Из устойчивой опоры один раз фиксирует bands шума и дрейфа. Полученные bands не расширяются ни шумной нижней точкой, ни повтором.
4. Спускается не ниже `floor_code` дискретными ограниченными шагами. После фактически достигнутой команды ждёт устойчивую точку; нормальное остывание выхлопа после снижения команды само по себе не является причиной отказа.
5. Требует обусловленный командой температурный отклик: хотя бы один канал должен измениться больше заданного статистического порога. Общего знака у выхлопа и горячего воздуха нет: один может снизиться, другой вырасти.
6. Только после успешной первой оценки точки разрешает нормальный возврат на опору. Затем повторяет ту же нижнюю точку и сравнивает:
   - обе устойчивые точки;
   - возврат опоры;
   - согласованность знака и величины переходов «опора → низ → опора → низ» хотя бы по одному статистически различимому каналу; второй канал всё равно обязан оставаться в фиксированных bands;
   - время установления.
7. После повторно принятой точки ещё раз возвращается на опору перед следующим снижением. На `floor_code` строит результат: `min_code` — предыдущая, уже повторно проверенная точка; самая нижняя точка остаётся запасом. `max_code` — испытанная опора `ceiling_code`.
8. В профиль попадают отдельные максимально **наблюдавшиеся** `tested_slew_up_codes_per_s` и `tested_slew_down_codes_per_s`. Это запись факта при частоте вызова `tick`, а не автоматическое объявление более быстрого перехода безопасным.

Таким образом ровная полка свежих, но зависших данных не завершает цикл: нет ответа на команду. Медленное остаточное тепло, которое похоже на полку, должно нарушить воспроизводимость возвратного/повторного перехода или привести к тайм-ауту. Это повышает отбраковку, но не превращает две температуры в датчик пламени.

## Отказы и временные границы

Во всех активных фазах `operator_negative`, сбой контекста RUN/топлива/свечи, невалидный `status`, stale-данные, повторные/регрессирующие timestamps, чрезмерный skew, разрыв выборок, команда вне интервала или слишком быстрый фактический переход завершают процесс с `stop_requested`.

- Времена монотонны: `now_ms` назад даёт `BACKDATED_TIME`.
- Дедлайны включительны: при `elapsed >= timeout` принимается отказ, а не новая точка.
- Расчёты основаны на вычитании уже упорядоченных времён; нет сложения `now + timeout`, поэтому переход возле `uint64_t::max()` не переполняет дедлайн.
- Одинаковые timestamps допустимы между быстрыми вызовами `tick`, но отсутствие новой согласованной пары до `maximum_no_new_sample_ms` даёт `REPEATED_SAMPLE`.
- Неуспех не меняет результат на успешный и не порождает запрос следующей/более высокой команды. Увеличение до опоры происходит только по нормальной ветви после успешной оценки предыдущей точки.

## Интеграция в контроллер

`calibration_runtime.cpp` связывает ядро с обычным PREPURGE/PREHEAT/IGNITION/VERIFY/RUN, общим PI/формирователем в ручном режиме, приоритетным STOP и NVS-задачей. Диапазон передаётся на запись только после температурно завершённого охлаждения до IDLE; до подтверждения записи повторный START запрещён. Отмена/неопределённость/ошибка не заменяют прежний диапазон. Непрерывный профиль не переносится на другую конфигурацию процесса: проверяется fingerprint.

Стартовая статистическая политика реализации: три окна по 60 отсчётов с периодом 1 с; около десяти равных интервалов явно заданного диапазона; до 30 мин на опору/точку и 6 ч на весь цикл. Полы шума/дрейфа 0,25 °C, потолки опоры 2/1 °C, минимально различимый отклик 2 °C, множители 3. Это назначенные критерии анализа, не доказанные огневые границы; изменения находятся в одном `start_calibration_run()`. Огневые параметры и допустимый исследовательский интервал по-прежнему не имеют выдуманных значений по умолчанию.

Наблюдаемый целочисленный PWM учитывает квантование через ограниченный бюджет одного кода. Он разрешает округление медленного непрерывного задания, но не даёт дополнительный код заново на каждом 20-ms цикле. Программный тест отдельно отвергает такое накопленное превышение. Мгновенные `tested_slew_*` у целочисленной команды включают квантование; они не используются как разрешение ускорить мотор. Сохраняемые относительные темпы применяются к более узкому итоговому диапазону, поэтому абсолютный темп не становится выше испытанного задания.

- включительную границу общего дедлайна и явный `cancel()`.
