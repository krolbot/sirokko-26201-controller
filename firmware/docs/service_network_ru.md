# Сервис Wi-Fi / MQTT / OTA — 0.1.8-DRAFT

Переход draft-05→draft-06 нельзя делать удалённым обновлением старой платы: требуется ручная аппаратная интеграция четырёх кнопок и удаление старого NC STOP/J22. Старый NVS не даёт новую приёмку. Ни наличие USB, ни подпись OTA не доказывают совместимость проводки. Только BENCH, опасные нагрузки отключены.

Реализация подготовлена для будущего доступа, отдельно разрешённого владельцем. Плата не подключена, действующие ключи/брокер/туннель сейчас не настроены. Это не отчёт об успешной аппаратной OTA. Не создавались серверы, публичные порты или облачные службы. Локальное управление не зависит от сети или календарных часов.

## Первичная настройка по USB

Без сохранённой настройки `sirokko_net/config_v1` устройство работает автономно; открытая точка доступа и web-интерфейс не создаются. Для Wi-Fi требуются WPA2 или выше и PMF; MQTT — только `mqtts://` с username/password, CA и проверкой имени сервера. Та же CA используется для HTTPS обновлений. SNTP нужен только для времени проверки TLS-сертификатов; недоступное время не должно выключать локальное управление, но сервис до синхронизации не соединяется.

Владелец готовит защищённый временный JSON (0600, без помещения в Git/чат/карточку): строковые поля `ssid` (до 32 байт), `wifi_password` (64), `broker` (191), `username` (64), `password` (128), `ca` (4095, PEM), `update_public_key` (1023, PEM RSA-3072). Broker URI не содержит userinfo. Действительные значения берутся из менеджера секретов, а не передаются в переписке. Приватный ключ подписи на плату не загружается.

Из `firmware/`: `python3 tools/service_artifacts.py usb-import --config /защищённый/config.json --output /защищённый/usb-command.txt`. Утилита требует закрытые права входа, создаёт новый файл 0600 и не выводит содержимое. Файл содержит единственную команду `network import <base64 JSON>` для защищённой локальной USB-сессии. Отключить запись сеанса и локальное эхо, передать файл напрямую, удалить временные копии. Base64 не является шифрованием. Прошивка не печатает значения, стирает временные буферы и отвечает только `network=SAVED|REJECTED; reboot required`.

Импорт и `reboot` возможны только через локальную flash lease при реально применённых командах OFF. В неквалифицированном профиле локальный ремонт разрешён лишь когда никакой обдув/топливо/накал/START не активны; это не открывает OTA или пуск. Во время RUN импорт/reboot запрещены. После настройки нужен reboot; неверные сетевые данные не изменяют commissioning и не создают автозапуск.

Без flash encryption NVS не защищает Wi-Fi/MQTT секреты от физического чтения flash. eFuse, secure boot и flash encryption этой задачей не включались. Это явная граница угроз: приложение проверяет подписанное задание, но загрузчик не объявляется криптографически защищённым от физической перепрошивки.

## Темы и права

Идентификатор: `sirokko-<12 hex MAC>`; база совпадает с MQTT client_id.

| Тема | Направление / свойства |
|---|---|
| `<base>/telemetry` | Плата → сервис, QoS0, не retained, примерно раз в 2 с. |
| `<base>/availability` | Online/LWT offline, QoS1, retained. Сетевой признак, не доказательство работоспособной горелки. |
| `<base>/service/request` | Сервис → плата, QoS1, ОБЯЗАТЕЛЬНО retain=false. Только read/stop/update. |
| `<base>/service/reply` | Плата → сервис, QoS1, не retained, `{"seq":число,"code":"код"}`. |

У брокера заранее нужны индивидуальные учётные данные и ACL: устройство читает только свою request-тему и пишет только свои telemetry/availability/reply, оператор — наоборот. Другие устройства/анонимные клиенты не должны иметь права публикации request. Не считать туннель заменой TLS/ACL/подписи. Брокер и его ACL в этой задаче не развёрнуты и не испытаны.

Telemetry содержит version/board, nonce, `last_sequence`, uptime/boot/session, состояние/faults/start_block, config schema/revision/low qualification, настройки, raw/calibrated room, EXH/AIR, качество/возраст/MAX faults, команды вентилятора/муфты/свечи/permit, safety/storage, время этапа, update flag и счётчики. Температуры — целые mC, скорость — 0..1000 permille. `command_starts`, `failed_ignitions`, `command_run_ms`, `command_glow_ms` — десятичные СТРОКИ uint64, чтобы JSON/JavaScript не терял точность. SensorQuality и start_block — enum из `control.hpp`; неверное качество важнее отображённого числа. `safety_ok` — отдельный аппаратный вход; команды выходов не являются измеренными контактами.

## Задание и защита от повторов

JSON — один плоский объект, до 2047 байт, не более 20 полей, без duplicate keys, вложенности, NUL и хвостового мусора. Фрагментированные/retained сообщения отклоняются. Общие поля:

- `op`: только `read`, `stop`, `update`;
- `nonce`: 32 hex символа из СВЕЖЕЙ telemetry текущего MQTT-соединения;
- `seq`: uint32 > последнего принятого seq, в том числе после INVALID/FORBIDDEN;
- `uptime_ms`: копия свежего uptime платы, а не часы компьютера;
- `ttl_ms`: 1..30000; возраст проверяется монотонным uint32 difference.

Reconnect меняет криптографически случайный nonce и сбрасывает sequence. Старая очередь update привязана к старому nonce и отбрасывается. MQTT clean session включён; старый nonce, повторный seq или просрочка не исполняются. При переполнении seq нужен новый сеанс соединения, а не перезагрузка горелки.

`stop` выставляет запрос общему автомату, не трогает GPIO в сетевой задаче. STOP_REQUESTED — принятие запроса, а не подтверждение уже законченной продувки; смотреть state и команды в telemetry. `read` отвечает OK. Нет MQTT START, RESET, settings/config, ручных fuel/glow или обхода safety; неизвестный op — FORBIDDEN.

`python3 tools/service_artifacts.py request --operation read|stop --telemetry /путь/свежая-telemetry.json --output /путь/request.json` готовит пакет, но НЕ публикует его. Для нескольких операторов seq координируется (`--sequence`); одновременно подготовленные одинаковые seq безопасно отвергаются. Передать через разрешённый TLS MQTT-клиент с retain=false, пока не истёк TTL. При невалидном nonce/формате/retained ответ может отсутствовать: это намеренное отклонение, не успешное выполнение.

## Подпись OTA

Файл — только `sirokko_26201_controller.bin`, не merged image/bootloader/разделы. Дополнительные поля update: target=`esp32s3`, board=`ESP32-S3-DevKitC-1-N8R8-v1.1`, schema=4, version=`N.N.N-DRAFT` (компоненты 0..99, строго новее работающей), size (1024..размер слота), lowercase SHA-256, HTTPS URL без credentials/CR/LF, signature (Base64, 384 байта RSA-3072).

Подписывается SHA-256 следующего UTF-8 сообщения, RSA PKCS#1 v1.5, с LF после КАЖДОЙ строки, включая последнюю:

```text
SIROKKO-OTA-1
esp32s3
ESP32-S3-DevKitC-1-N8R8-v1.1
4
<version>
<decimal size>
<lowercase sha256>
<exact https URL>
```

Приватный RSA-3072 ключ остаётся у владельца в менеджере ключей. Временный экспорт только 0600; не аргументом/переменной со значением секрета, не в логах/Git. Утилита использует штатный OpenSSL, не создаёт рабочий ключ автоматически и не подменяет подпись пустой. Например для СЛЕДУЮЩЕЙ проверенной сборки:

```sh
python3 tools/service_artifacts.py sign --image /путь/новый.bin \
  --version 0.1.8-DRAFT --url https://разрешённый-сервер/новый.bin \
  --key /защищённый/ключ.pem --output /путь/signed-image.json
python3 tools/service_artifacts.py request --operation update \
  --telemetry /путь/свежая-telemetry.json --manifest /путь/signed-image.json \
  --output /путь/request.json
```

Эти команды только создают локальные артефакты; подпись не доказывает совместимость произвольного bin. До подписи проверить образ штатным esptool и сопоставить SDK/schema/target/board/тесты/manifest. Сервер должен отдавать точный Content-Length и HTTP 200 без redirect. URL входит в подпись. Размещать файл и публиковать request только после отдельного разрешения доступа; в этой задаче ничего не загружено на OTA-сервер и не отправлено плате.

## Исключительное обслуживание и ответы

VALIDATING означает постановку одного задания в ограниченную очередь, не готовность flash. Проверяются подпись/слот/срок, затем control task единолично подтверждает lease: полная остановка/продувка/recovery, холодные исправные датчики, принятый профиль, нет STOP/START, здоровый выходной адаптер. После применения OFF на GPIO снимаются ARM/heartbeat, удерживается SW_TRIP и START блокируется до освобождения/перезагрузки. «Физически применено» здесь означает успешный SDK-вызов, не независимое измерение контакта.

| Код | Значение |
|---|---|
| OK / STOP_REQUESTED / VALIDATING | Чтение / запрос штатного STOP / начало проверки задания. |
| BUSY | Работающий этап, продувка, конкурирующий START/lease или изменение условий. OTA не останавливает горелку ради себя. |
| CONFIG / SENSOR / HOT / OUTPUT | Профиль/настройки, качество/свежесть датчика, охлаждение или выходной путь не допускают обслуживания. |
| INVALID / FORBIDDEN | Неподходящие поля/schema/target/version либо запрещённая операция. |
| SIGNATURE / OVERSIZE / EXPIRED / REPLAY | Неверная подпись, слот мал, истёкшее задание или старый сеанс. |
| IO / SIZE / TARGET / HASH | TLS/NVS/SDK ошибка, HTTP/длина не совпадают, описание образа не совпадает, SHA-256 flash не совпадает. |
| REBOOTING | IDF проверил полный образ и выбрал следующий boot slot; подтверждение health будет уже после загрузки. |

До скачивания и перед выбором образа сохраняются счётчики/история/настройки и объединённая маска текущих/ещё не сброшенных NVS-аварий. OTA не стирает аварию из-за неуспевшего обычного snapshot. Порядок записи отдельных NVS-ключей не объявляется общей транзакцией.

При потере сети/nonce/lease, неполном образе, неверном хэше/подписи/описании вызывается abort, прежний boot не меняется. Потеря сети/обрыв питания физически на S3 ещё не испытаны. После успешного OTA — обычная RECOVERY_PURGE, не восстановление RUN. START запрещён, пока pending image не проверен: не менее 5 с, 200 проходов control, свежие датчики, живой TFT/output/NVS. После безопасного OFF выполняется mark-valid; при неуспехе/60-секундном timeout — штатный rollback, если есть предыдущий valid image. Отказ control не поддерживается отдельным heartbeat.

## Разделы, совместимость и USB recovery

8MB: NVS `0x9000/0x6000`, otadata `0x10000/0x2000`, ota_0 `0x20000/0x300000`, ota_1 `0x320000/0x300000`; остальные разделы — `partitions.csv`. Фактический размер/остаток обоих слотов приведён в manifest комплекта, а не угадан.

Переход с 0.1.5 с factory-only layout требует ПЕРВОЙ локальной USB-записи нового bootloader/partition table/app/ota_data_initial по НОВОМУ `flash_args`. Старый адрес app `0x10000` больше недопустим. Не прошивать работающий отопитель и не подключать топливо при первичной проверке. Не выполнять erase_flash и не стирать NVS автоматически. Сначала снять питание силовых нагрузок и сохранить конфигурацию/NVS как секретный локальный файл; конкретный порт/физический доступ согласовать отдельно.

Из каталога `firmware/` готового комплекта, в официальном ESP-IDF окружении: `python -m esptool --chip esp32s3 write_flash @flash_args`. Это инструкция владельцу, не выполненная здесь прошивка. Запись по штатному CLI и загрузочный режим ESP32 остаются аварийным путём, когда сеть недоступна. Для возврата к старой factory-разметке потребуется её полный USB-комплект, не OTA downgrade.

Schema 1/2 профиля не повышается и не принимается молча. Повреждённые/неизвестные records сохраняются и блокируют START. Откат не меняет NVS и не восстанавливает старую приёмку; старый образ, не понимающий новый профиль, обязан отказать в пуске. Это не обещание произвольной двусторонней миграции будущих схем. Перед несовместимым обновлением требуется отдельный испытанный план миграции и восстановления.
