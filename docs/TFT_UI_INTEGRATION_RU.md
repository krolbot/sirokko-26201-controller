# TFT 320×240 — интеграция в прошивку

## Результат и границы

Утверждённые экраны перенесены в реальный C++ renderer поверх существующего `esp_lcd`/ST7789, без LVGL. Горизонтальная композиция сохранена: рабочая дуга, отдельные текущая температура и уставка; на остановленном экране — серая дуга без маркеров. Код проверен на host и собран ESP-IDF v5.2.3 для ESP32-S3. Это локальная разработческая сборка поверх `f937979029b2b248cd482d9ed30da0c794c28b24`, не новый опубликованный релиз и не результат испытания устройства.

PCB, GPIO, control core, runtime API и web не менялись. Исходная утверждённая HTML-галерея сохранена: SHA-256 `0a140fbe3a91278c056e76797b8662f4e444d816e43722b4e0b26a2e3ae5cab9`.

## Реализация

- `panel_ui.*`: меню из восьми пунктов с четырьмя видимыми строками; один таймер отключения. В IDLE задаётся интервал следующего ручного пуска, в активном сеансе — срок выключения от текущего момента; ноль выключает таймер. Отложенного пуска в панели нет.
- `panel_canvas.*`: переносимый RGB565 Canvas со сглаживанием, Roboto/кириллицей и заранее растеризованными SVG-иконками. Шрифты и иконки генерируются воспроизводимо; OFL и исходный шрифт находятся в `firmware/assets`. В runtime не нужны FreeType, Python или SVG-интерпретатор.
- `panel_render.*`: один и тот же renderer для прошивки, PNG и демонстрационного видео. Перемещение маркеров — 180 мс, смена экрана — 200 мс, выделение меню — 140 мс. Вентилятор вращается только на соответствующих активных этапах, период — 2000 мс. Числовые показания не интерполируются.
- `panel_damage.hpp`: хеши плиток 32×16 уменьшают передачу неизменившихся областей. Это только оптимизация графики, не часть защиты.
- `panel.cpp`: одна DMA-передача за раз, полоса 320×16. Два буфера по 10240 байт: выходной DMA и вспомогательный для перехода, всего 20480 байт. Полный framebuffer не требуется. RGB565 внутри Canvas — native endian; на SPI отправляется big endian. Сохранён BGR.
- Геометрические циклы используют float для FPU ESP32-S3, ограничиваются областью примитива и текущей полосой. После этой оптимизации все 36 контрольных кадров побайтно совпали с кадрами до неё.

## Волна нагрева и сближение точек

В `panel_render.cpp` внедрён принятый мягкий световой проход внутри насыщенно-оранжевого участка от измеренной температуры к уставке. Это только представление: control core и числовые показания не изменяются. Размеры обеих точек сохранены; при росте измерения сокращаются расстояние между ними и длина участка. В точке совпадения малая точка оказывается под большой. При снижении температуры малая точка снова отходит от уставки — искусственного движения к цели нет.

- Цикл — 2400 мс: проход 1900 мс и пауза 500 мс. Огибающая смягчает начало и конец; свет не пересекает маски маркеров и не затрагивает текст, серую или светлую части дуги.
- По мере сокращения углового разрыва амплитуда падает линейно: полный уровень при 27°, ноль при 10°. На шкале 15…30 °C / 270° это соответствует разрыву примерно 1,5…0,56 °C. Ниже свет выключен, но точка продолжает следовать измерению.
- Условия: RUN, включённый fuel output, температурный режим, свежий валидный датчик, нет аварии/калибровки; сцена нагрева или нагрева с таймером. Равенство/превышение реальной уставки отключает эффект сразу, даже если графическое сглаживание ещё не закончилось. Уменьшение уставки ниже текущего измерения проверяется так же.
- STOP/fault прерывают анимацию после текущей безопасной DMA-передачи; это проверено на harness реального `panel.cpp`. При выключенном fuel стационарный экран не создаёт повторных передач.
- 720 кадров по сетке температуры/фазы побайтно совпали с ранее принятым standalone-прототипом, включая крайние положения и кардинальные точки дуги. Для каждого проверено совпадение полной картинки и 16-строчной отрисовки. В штатных тестах добавлены маска пикселей, направление, пауза, 14 неактивных состояний, резкие изменения показаний/уставки и движение точки в обе стороны.
- Пересозданы 36 PNG: изменились только `heat` и `timer-running` за счёт добавленного эффекта; остальные 34 побайтно совпали с предыдущим комплектом. Видео `TFT_heat_approach.mp4` содержит 375 кадров / 15 с при 25 FPS; показания 20→26 °C специально ускорены в тестовом источнике, уставка 26 °C постоянна. CSV сохраняет входные показания и графическую координату маркера. Это не запись отопителя и не измерение скорости нагрева/TFT.

## Состояния и безопасность представления

Один снимок фиксируется на весь кадр. STOP, авария, потеря необходимых данных и защитные этапы не ждут окончания обычной анимации: оставшаяся отрисовка отменяется после текущей передачи. При пропавшем DMA callback через 250 мс отключается неисправный дисплейный путь; буфер не освобождается и не переиспользуется. KEY0 и control task остаются независимыми от панели.

Команда из меню не объявляется выполненной при попадании в очередь: «Применение» остаётся до совпавшего свежего snapshot. При истечении 5 с показывается «Нет подтверждения» / «Проверьте значение», а не ложное утверждение об отклонении или неизменности значения. Смена boot/state, STOP, fault и потеря snapshot отменяют старые клики/черновики. Полноэкранные этапы запуска, калибровки, обслуживания и отсутствия датчика не допускают скрытого управления меню под ними.

`VERIFY` подписан «Проверка запуска»: это проверка температурных признаков, не доказанное обнаружение пламени. Проценты прогресса и время окончания охлаждения не выдумываются. Таймер не отменяет продувку, охлаждение и защиты.

## Воспроизведение

Из корня репозитория:

```sh
python3 firmware/tests/run_host_tests.py
/usr/bin/python3 firmware/tools/generate_panel_fonts.py --check
/usr/bin/python3 firmware/tools/generate_panel_icons.py --check
/usr/bin/python3 firmware/tools/preview_panel.py --output firmware/build-host/preview --video --approach
```

Для предпросмотра нужны g++, Pillow; для видео — ffmpeg. Для регенерации иконок нужен rsvg-convert. Они не нужны в устройстве или для обычной сборки готовых `.inc`.

Целевая сборка использовала образ:

```text
espressif/idf@sha256:9cd723f013e1a8b22aeed61c02e3248bb11e8f2e2ae333cee08a18b9e36c1380
```

В ESP-IDF v5.2.3, из `firmware`:

```sh
idf.py -B build-tft -D SDKCONFIG=build-tft/sdkconfig -D IDF_TARGET=esp32s3 build
```

Проверенная конфигурация: native 240×320, rotation=90, logical 320×240, gaps=0, invert=y, SPI 20 MHz, FreeRTOS tick=1000 Hz. Существующий `sdkconfig` другого build-каталога не перезаписывался.

## Что не измерено на устройстве

Ориентация, RGB/BGR, offsets/inversion конкретного TFT, его читаемость, EC11/KEY0 и скорость анимации физически не проверены. Планировщик стремится начинать кадр раз в 40 мс, но это не обещание 25 FPS. Чистая передача полного кадра при 20 MHz: `320 × 240 × 16 / 20000000 = 0,06144 с`, то есть максимум около 16,28 полных кадров/с ещё без накладных расходов. Частичные обновления сокращают этот объём. Видео 25 FPS — программная демонстрация, не измерение TFT; фазы в нём ускорены и значения тестовые.

Не выполнялись прошивка устройства, AP/OTA reboot/rollback, включение силовых выходов или огневые испытания. Не изменялись Secure Boot/eFuse/Flash Encryption. Физическая квалификация горения и силовой части остаётся отдельной от выполненного графического этапа.
